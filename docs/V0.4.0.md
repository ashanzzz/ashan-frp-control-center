# v0.4.0 Resource Console & Provider UX

## Product model

v0.4.0 separates four facts that were previously easy to confuse:

1. **Provider connectivity** — whether ChmlFrp / Cloudflare APIs are actually reachable now.
2. **Provider resources** — remote ChmlFrp tunnels/nodes and Cloudflare DNS records.
3. **Ashan desired state** — the local managed tunnel plans and the single GLOBAL ACTIVE/STANDBY policy.
4. **FRPC runtime state** — whether the generated configuration is actually connected and healthy.

A saved token is no longer presented as the successful terminal state. The WebUI uses `Connected`, `Disconnected`, `需要 Zone`, or `未配置` based on live health.

## Settings UX

- ChmlFrp and Cloudflare save/test results are shown **inside their own provider cards**, where the user clicked.
- Saving immediately performs a live verification and leaves the result visible in the card.
- Re-entering Settings refreshes the live dashboard first, so a valid saved provider shows `Connected`, not stale `Configured`.
- ChmlFrp panel copy now explicitly asks for the API Token and warns against pasting browser OAuth URLs containing access/refresh tokens.
- Settings now owns only provider connection data and GLOBAL ROUTING policy. Resource CRUD moved to the provider resource pages.

## Overview

Six global cards now show:

- ChmlFrp API
- Cloudflare
- ACTIVE
- STANDBY
- FRPC
- GLOBAL HA

The overview also reports managed tunnel health, unmanaged ChmlFrp resources, and Cloudflare record count. If ACTIVE is not initialized while ChmlFrp is connected, an onboarding banner opens the routing bootstrap workflow.

## Tunnel management

- Managed plans and unmanaged ChmlFrp resources are separated.
- Existing ChmlFrp tunnels can be imported one at a time or in bulk.
- Importing creates only a local Plan and does **not** silently mutate the provider.
- Bulk import defaults to `dns_managed=false`.
- `解除纳管` removes only the local Plan; remote ChmlFrp and Cloudflare resources remain unchanged.
- Managed tunnel node selection remains globally controlled and cannot be changed per tunnel.

## ChmlFrp console

- Read all remote tunnels.
- Read nodes, node state, role and quarantine state.
- Create a remote tunnel.
- Edit an **unmanaged** remote tunnel.
- Import a remote tunnel into Ashan management.
- Run read/config-generation diagnostics.
- Run an explicit safe write diagnostic on an **unmanaged** tunnel by submitting its current values unchanged and re-reading the resource for equality.
- Managed remote resources are protected from direct editing.
- ChmlFrp v2 tunnel deletion remains capability-gated because the official v2 delete endpoint is documented as unavailable. The UI explains the limitation instead of pretending the delete succeeded.

## Cloudflare DNS console

- Read the complete record list for the selected Zone.
- Create records.
- Edit records.
- Delete records.
- Supported editor types in this release: A, AAAA, CNAME, TXT and MX.
- Ashan-managed HA A records are visibly marked and protected from direct edit/delete.
- Manual DNS deletion writes a pre-delete snapshot into Activity.
- For editor-supported record types, the DNS page keeps the just-deleted snapshot and offers an immediate one-click restore action.
- A full API diagnostic creates a temporary TXT record, reads it, updates it, deletes it, verifies cleanup, and records the test in Activity.

## GLOBAL ROUTING bootstrap

- The first ACTIVE/STANDBY assignment has a dedicated bootstrap endpoint and dialog.
- Existing ChmlFrp tunnel distribution is displayed before choosing ACTIVE.
- Bootstrap validates that selected nodes are online.
- Bootstrap saves policy only; it does not silently migrate provider resources.
- Once ACTIVE exists it remains locked; future ACTIVE changes use GLOBAL FAILOVER.

## Safety / invariants retained

- All managed tunnels share one ACTIVE node.
- No per-tunnel failover.
- ChmlFrp is the tunnel configuration source.
- FRPC runtime verification precedes managed Cloudflare DNS switching.
- Local/auth/config failures do not become node failovers.
- Provider CRUD cannot bypass the GLOBAL HA ownership rules for managed resources.
